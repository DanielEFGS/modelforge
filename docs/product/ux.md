# UX Specification

## Core layout

Desktop:

```text
+---------------------------------------------------------------+
| ModelForge | target controls | privacy | theme/help           |
+---------------------+----------------------+------------------+
| SOURCE              | MODEL                | OUTPUT           |
| JSON editor         | inferred tree/table  | generated files  |
|                     | editable semantics   | code preview     |
|                     | diagnostics          |                  |
+---------------------+----------------------+------------------+
| status / compatibility / Generate / Copy / Download          |
+---------------------------------------------------------------+
```

The workspace is the product. Marketing copy does not push it below the fold.

## Desktop behavior

- Source panel: approximately 32% width.
- Model panel: approximately 31% width.
- Output panel: approximately 37% width.
- Panels are resizable only after MVP unless implementation is trivial and accessible.
- Output file tabs appear when a target generates multiple artifacts.
- Generation can be automatic with a short debounce for cheap plain-language targets, but Spring bundle generation should still have an explicit Generate control if automatic updates create distracting churn.

Preferred MVP: explicit Generate after parsing/inference; regenerate when target options change only after user has generated once.

## Mobile behavior

Do not squeeze three editors horizontally.

Use a step/tab model:

```text
[1 Source] [2 Model] [3 Output]
```

- persistent compact target summary,
- clear Next/Generate action,
- no horizontal page overflow,
- editor height respects mobile viewport and virtual keyboard,
- Copy/Download remain reachable without overlapping browser chrome or ads.

## Source state

Actions:
- Paste JSON
- Load example
- Clear

States:
- Empty
- Valid JSON
- Invalid JSON
- Parsed with warnings

Syntax errors must include line/column where feasible and a human description.

Never replace user input automatically.

## Model inspector

Each field row shows:
- source key,
- generated property name,
- inferred type,
- required/optional,
- nullable,
- semantic hint where present,
- warning marker where evidence is incomplete.

Example:

```text
email_address -> emailAddress | string | required | hint: email
created_at    -> createdAt    | string | required | hint: datetime
items         -> items        | unknown[] | warning: empty array
```

Clicking a row opens compact editing controls.

## Compatibility UI

Example:

```text
Spring Boot 4.1.x
Java 11

INCOMPATIBLE
Spring Boot 4.1 requires Java 17 or newer.
Recommended: Java 21 LTS.
```

Do not let users believe incompatible output is verified.

Possible actions:
- “Use recommended Java 21”
- change target manually.

## Output

Output must show metadata outside the generated code:

```text
Target: Spring Boot 4.1.x
Verified profile: 4.1.1
Java: 21
Artifacts: Entity, DTO, Repository
```

Buttons:
- Copy current file
- Copy all (plain targets)
- Download current file
- Download bundle/ZIP later when multi-file packaging is mature

Do not inject “Generated by ModelForge” comments into source code by default.

## Privacy communication

Visible near the source editor:

> Local processing — your JSON and generated code stay in this browser.

A details link explains that analytics/ads may make normal network requests but never receive source/code content.

## Ads

There is no ad inside the workspace grid.

Desktop candidates:
- right side rail outside the workspace on sufficiently wide screens,
- one in-page unit after the workspace and before explanatory content.

Mobile:
- one in-content unit after successful tool area / below workspace,
- avoid anchors initially if they visually interfere with editor controls.

See `docs/growth/advertising.md`.

## Accessibility

- Full keyboard operation.
- Visible focus indicators.
- Tab order follows Source -> Model -> Output -> actions.
- Target selectors have real labels.
- Diagnostics use text/icon, never color only.
- Code editors have accessible labels.
- Contrast meets WCAG AA.
- Respect reduced motion.

## Visual direction

Developer-focused rather than neon “AI tool” aesthetics.

Suggested character:
- neutral/dark-capable UI,
- high information density without clutter,
- one restrained accent color,
- monospaced code but normal UI typography elsewhere,
- version chips and diagnostic states are visually clear.

The page must still look credible with ad slots empty.
